## 0. Audit (before coding)

- **Bootstrap:** `/auth/bootstrap` plus anonymous `POST /projects` already existed and the login page
  had a create form. It failed on a fresh clone because `data/` does not exist: SQLite could not open
  `data/app.db`, so the server crashed at startup. The login page then hid the network error
  and showed an empty sign-in form.
- **Layering:** every dropdown, menu, popover and tooltip is already a Radix portal on `<body>`, so
  stacking is decided only by tokens. `--z-dialog` (300) was above `--z-dropdown` (100) and
  `--z-popover` (150), so lists opened from a dialog rendered underneath it. 25 raw z-index numbers
  were scattered across feature CSS.
- **Where things live:** entity data `backend/app/services/entity_service.py` + `EntityInspectorTab`;
  tasks and Gantt `api/v1/tasks_routes.py`, `features/tasks/GanttView.tsx`; Users `features/users/UsersPage.tsx`
  (`/users?section=…`, which also hosts the admin console); Admin/Rules `features/admin/*`;
  Settings `features/settings/*` (`/settings?section=…`); /me `features/me/*`.
- **Versioning UI to reuse:** `features/entities/ProductsColumn.tsx` (version list with star for
  MASTER, ascending numbers, comment, author, date) is the pattern for schedule versions (§5).
- **Expensive or risky items (decide before phases D–E):**
  - Calendar (§4) is a custom virtualized timeline: the largest item in this CR, roughly the size of
    the existing Gantt. It is feasible but slow to build. It is planned last so it can reuse Phase D's
    draft and version layer.
  - XLSX export (§10): use **XlsxWriter** (BSD-2-Clause, Python, `constant_memory` streaming)
    server-side. SheetJS on npm is outdated (newer builds only ship from their own CDN) and
    ExcelJS is MIT but keeps whole workbooks in memory, so neither is the first choice.
  - "Migrations must work on PostgreSQL": project DBs are per-project SQLite files by design.
    Migrations are still tested on PostgreSQL through the existing testcontainers test, which is
    skipped when Docker is not available.
  - Draft conflict detection (§5) compares live `updated_at`/values captured when the draft started.
    It does not merge automatically; conflicts are listed at save time.

## Phase B — Confo grid (delivered)

**Where:** Tasks panel → **Confo** view (hidden for clients). Backend `app/api/v1/confo_routes.py`,
`app/services/confo_service.py`, models `app/models/confo.py`, migration `0006_confo`.

**Storage:** `confo_columns` (definition: key, label, type, options, default, validation, order,
default visibility, `edit_roles`, `deleted_at`), `confo_values` (one row per cell with one typed
column per storage kind: text, int, float, bool, date, user FK, entity FK) and `confo_value_items`
(multi-select choices). There is no JSON blob for values. The existing free-form `entity_data`
(Inspector) is untouched.

**Types:** text, integer, decimal (accepts `3,5`), yes/no (yes/no/sí/x/1/0), single select, multi select
(`a, b` or `a; b`), date (`YYYY-MM-DD` or `DD/MM/YYYY`), URL, user (username, full name or id), colour
(`#rgb`/`#rrggbb`), entity reference (path, unique name or id). Validation covers required, min/max,
pattern and max length. A default is shown for entities with no stored value and used in exports.

**Editing:** typed in-cell editors, Excel-style paste (a block, or one value into every selected cell),
Delete clears, undo/redo (Ctrl+Z / Ctrl+Y and buttons; each undo is sent to the server, so it is
permission-checked and audited too). Every batch is all-or-nothing, and rejected cells get a dashed outline,
a "!" marker and the message as a tooltip. Changes are audited as `confo.cells.update` with before/after values.

**Columns:** create, edit, reorder by drag, rename (key and label), soft delete with confirmation,
restore within 30 days, then automatic purge or "Delete forever". A column's type cannot change
while it holds values.

**Grid:** grouping by path hierarchy, entity type or none (collapsible); sort, per-column filters,
search, range selection, copy (TSV), paste, hide/unhide columns and rows, freeze 0-3 leading
columns, resize, saved views (per user, `saved_views` kind `confo`). The last-used layout is also
remembered in the browser.

**CSV export:** exports the current filtered view with visible columns only. Hidden rows are left out;
rows inside collapsed groups are included because collapsing is navigation, not filtering. UTF-8 with a
BOM, and cells starting with `= + - @` are escaped against spreadsheet formulas. Styled XLSX comes in phase E.

**CSV import:** comma, semicolon or tab separated, up to 10 MB / 20,000 rows. Rows match automatically by id/uuid,
then path, then name columns (you can override this). Header-to-column mapping is suggested and can be changed,
including creating new typed columns. The preview shows matched / unmatched / ambiguous / duplicate / to-create
rows and per-cell errors, with a downloadable error report. Commit is all-or-nothing, and empty cells leave
values unchanged. Entities are only created when **Create entities for unmatched rows** is ticked
(this needs `entity.manage`). Because entity creation touches disk, created entities are archived again if
the value write fails.

**Permissions:**

| Action | Rule |
|---|---|
| View | `task.view` other than `none`/`shared`. Clients get 403. Scoped users (artist `mine`, external `company`) only see entities with a task they can see. |
| Edit values | New permission `confo.edit` (seeded `all` for admin and producer; configurable in Roles). Limited to visible rows and to the column's `edit_roles`. |
| Manage columns | `confo.edit` = `all`. |
| Import | `confo.edit`; creating new columns also needs manage. |

Seeding now adds permission keys introduced later to existing projects without touching edited scopes.

## Phase C — studios, working hours, activation periods (delivered)

**Backend:** migration `0007_people_scheduling`, models `app/models/scheduling.py`, service
`app/services/availability.py` (pure maths plus loaders), routes `app/api/v1/people_routes.py`.

- **Working hours (§8):**
  - Storage: `user_work_hours` holds weekday intervals in minutes; `user_work_exceptions` holds a day off
    (no interval) or special hours.
  - A user without custom hours uses the project calendar: working days, starting 09:00, for
    `hours_per_day`.
  - `GET`/`PUT /users/{id}/work-hours` validates HH:MM, start < end, no overlaps, and the IANA timezone.
    On Windows this needs the `tzdata` package, now a dependency.
  - Saving recomputes `daily_capacity_hours` as the average over the days that have hours.
  - The **workload heatmap** now uses per-day capacity: exceptions, then weekday hours, and 0 outside the
    user's activation periods. Bookings on a zero-capacity day show as over capacity (999.9%).
  - People edit their own hours on /me; others need `user.manage`.
- **Activation periods (§6):**
  - `activation_periods` has exactly one target (department, company or user) via typed foreign keys,
    plus a check constraint.
  - CRUD under `/activation-periods` needs `user.manage` or `task.edit_schedule`. Reading is open to
    internal roles; clients get 403.
  - No periods means always active.
  - `GET /schedule/warnings` lists tasks whose ideal dates fall outside the periods of an assignee, the
    task's department or the assignee's studio. These are warnings only, shown as a banner in task detail.
    Calendar editing and schedule versions use the same table in phases D/E.
- **Studios (§11):**
  - New company kind `client` (client users may belong to `client` or `external` companies).
  - `company_comments`: dated notes with author; anyone with `user.view` can add, while delete needs the
    author or `user.manage`.
  - `company_members`: links people to a studio or group in addition to their primary company.
  - All changes are audited.

**Frontend:**
- Users → Companies is now a master list plus side panel. The list is searchable, filterable by kind and
  grouped (Studios, External, Clients, Groups), with collapsible departments under each studio.
- The side panel has inline name/code editing, kind, colour, delete, a searchable department multi-select,
  members (primary or linked, with avatars, role and working hours at a glance), linking people,
  activation periods and comments.
- User editor: searchable department multi-select, read-only derived daily capacity, the per-weekday hours
  editor (several intervals per day, timezone, exceptions, reset to project default) and activation periods.
  Departments get a **Periods…** dialog. /me shows a summary and **Edit my hours**.

**Tests:**
- `backend/tests/test_cr04_people.py`: maths, API, warnings, workload capacity, and permission and
  client probes.
- `workHoursModel.test.ts`.
- `e2e/cr04_people.spec.ts`: restores the demo data afterwards.

## Phase D — drafts, schedule versions, Gantt, milestones (delivered)

**Backend:** migration `0008_schedule_versions`, models `app/models/schedule.py`, service
`app/services/schedule_service.py` (pure overlay, diff, merge, conflict and lateness functions plus a
transactional apply), routes `app/api/v1/schedule_routes.py`.

- **Draft (§5):**
  - One server-side draft per user (`schedule_drafts` and `schedule_draft_changes`). It survives reloads
    and is invisible to other users.
  - Changes are task date updates, task assignments, and milestone or activation-period
    create/update/delete. Changes to the same item merge, and a create followed by a delete cancels out.
  - Each change keeps the live values from when it was first touched (`base_json`).
  - Endpoints: `GET/DELETE /schedule/draft`, `POST /schedule/draft/changes` (validated with the normal
    permissions: `task.edit_schedule`, `task.assign`, `milestone.edit`, `user.manage`/`task.edit_schedule`),
    `DELETE /schedule/draft/changes/{id}` (per-change revert), and `GET /schedule/draft/preview`
    (differences plus conflicts).
- **Versions:**
  - `POST /schedule/draft/save` (comment required) checks conflicts (409 with the fields, unless
    `overwrite_conflicts`). It then applies everything in one transaction (with `TaskEvent` history, source
    `schedule`), stores an immutable snapshot `S0001…` (task dates and assignments, milestones, activation
    periods) with author, date, comment and a diff summary, clears the draft and audits.
  - An empty draft creates a baseline snapshot.
  - `GET /schedule/versions` marks the newest version identical to live as **current**.
  - `POST …/star` keeps at most one starred baseline.
  - `POST …/jump` turns the differences into a **new draft**; nothing live is touched.
  - `GET /schedule/versions/compare?a=&b=` accepts a version id, `live` or `draft`.
  - Versions and compare hide tasks outside the caller's scope.
- **Permissions:**
  - New `schedule.version` (default admin, producer, supervisor; scoped holders may only save changes to
    their tasks).
  - New `milestone.edit` (default admin, producer).
  - Clients get 403 on all draft and version endpoints.
- **Milestones and deliver dates (§7):**
  - `milestones` table: name, date, kind `deliver`/`milestone`, optional single target (department, user,
    entity, task, company, or none, via typed foreign keys), note, status, `client_visible`.
  - `GET /milestones` includes `late_task_ids` (target tasks finishing after the date). Clients only see
    shared milestones, without task ids.
  - Direct CRUD exists for list use; the Gantt and Calendar go through the draft.

**Gantt (§9):**
- **Edits go to the draft.** Moves, resizes, user/company reassign drags, undo/redo and milestone moves are
  all draft changes. Bars show draft values with a dashed border and ✎.
- **Collision push:** toggled with *Push dependents*; `scheduleModel.computeCollisionPush`.
  - Downstream tasks starting before their upstream finishes are pushed, keeping their length in working
    days and landing on working days.
  - The pushed bars are shown live while dragging (`data-pushed`).
  - Moves that can't be resolved are refused with a message: starting before an upstream, a push that would
    move a task you can't edit, or a loop.
- **Selection:** the selected bar gets a solid yellow `--highlight` border, linked upstream/downstream bars
  and arrows get dashed yellow, nothing is dimmed, and status colours stay. Esc or a click on empty space
  unselects.
- **Draft bar and versions:** *DRAFT: N changes* (review/revert each change, discard, save with a
  differences and conflicts confirmation), plus a **Versions** panel (current marker, star, comment,
  author, date, summary, compare, jump).
- **Milestones:** yellow rhombus with a vertical guide; deliver dates are larger and filled, milestones
  outlined, done ones dotted, and "!" marks late tasks. Create with *+ Milestone* or a double-click on the
  timeline; edit or delete with a double-click or the context menu; drag to move.

**Tokens:** `--milestone`, `--milestone-text`, `--milestone-size`, `--deliver-size`, `--draftbar-h`,
`--versions-panel-w` (contrast-checked in both themes).

**Tests:**
- `backend/tests/test_cr04_schedule.py`: overlay/diff/round-trip, merge, conflicts, lateness per target,
